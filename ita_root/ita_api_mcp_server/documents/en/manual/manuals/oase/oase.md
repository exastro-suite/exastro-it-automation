# OASE Feature Configuration and Usage

## Usage Procedure

The standard OASE configuration flow is performed in the following order:

1. **Register Labels**: In the "Label" menu group, use Label Creation and Label Assignment to define the labels used for events and set the conditions for assigning them. Deduplication can also be configured for redundant configurations.
2. **Register Filters**: In the "Rule" menu group's Filter menu, configure the label conditions used by rules.
3. **Register Actions**: In the "Rule" menu group's Action menu, register the processing to be executed when a rule's conditions are matched.
4. **Register Rules**: In the "Rule" menu group's Rule menu, configure the matching conditions and the actions to use.

## Basic Concepts of Events

An event is data created when a monitoring system (Zabbix, Prometheus, Datadog, etc.) detects a state change (service outage, high CPU load, etc.) in a monitored system. Exastro OASE retrieves this data and performs evaluation and automated response.

- Events ingested into OASE hold their information as a set of multiple labels (key-value pairs, e.g. `process: httpd`, `status: down`). Labels are set based on the configuration in the "Label Assignment" screen.
- System labels starting with "_exastro_" (fetch time, TTL, etc.) are automatically assigned to events.
- There are two types of events, "normal events" and "conclusion events," distinguished by the `_exastro_type` label. Normal events are those collected from monitoring systems, while conclusion events are generated by OASE after a rule match. Conclusion events are also subject to the evaluation flow, enabling chained automated responses.
- Processing order: label assignment → filter → rule evaluation → (on match) action execution.

### Event History Fields

| Field | Description |
|---|---|
| Object ID | Auto-numbered; not editable. |
| Event Collection Settings ID | Sourced from OASE Management / Event Collection / Event Collection Settings ID. |
| Event Collection Date/Time | Date/time when the agent retrieved the event. |
| Event Valid Date/Time | Date/time the event is considered valid. |
| Event State | One of: Under Review / Undetected / Evaluated / Timed Out. |
| Event Type | Event or Conclusion Event. |
| Labels | Assigned label information. |
| Evaluation Rule Name | Sourced from OASE / Rule / Rule Label Name. |
| Events Used | Events used in the evaluation. |

If settings are incorrect (e.g., misconfigured response key or event ID key), a label with the key `_exastro_not_available` is assigned and the event is ingested as an undetected event.

## Label Creation

Labels are attribute information assigned to events, consisting of key-value pairs. There are two kinds: "system labels" (`_exastro_event_collection_settings_id`, `_exastro_fetched_time`, `_exastro_end_time`, `_exastro_agent_name`, `_exastro_agent_version`, `_exastro_type`, `_exastro_checked`, `_exastro_evaluated`, `_exastro_undetected`, `_exastro_timeout`, etc.) automatically assigned by Exastro, and "user labels" configured by the user.

In the "Label Creation" screen, define the user label key (alphanumeric characters and `_-`, no symbols at the start, max 255 bytes), color code, and remarks. In the "Label Assignment" screen, set a fixed value or a specific field's value as the label value, based on conditions applied to specific fields of the received event. Assigned labels are used in filter conditions and rule evaluation.

## Label Assignment

Main input fields in the "Label Assignment" screen:

| Field | Description |
|---|---|
| Labeling Setting Name | Arbitrary setting name (max 255 bytes). |
| Event Collection Setting Name | Select a setting name registered in Event Collection. |
| Search Condition (key / value data type / comparison method / comparison value) | Specify an event key using JMESPath, and set the data type, comparison method (==, ≠, <, <=, >, >=, or RegExp variants), and comparison value. |
| Label (key / value) | The key and value of the label to assign. When using a regular expression, leave the value blank to use the match result as-is, or reference capture groups such as `\1`. |

Comparison method constraints by value data type:

| Value Data Type | Available Comparison Methods |
|---|---|
| String / Integer / Decimal | All except RegExp variants |
| Boolean / Object / Array / Empty check | ==  (match) and ≠ (mismatch) only |
| Other | RegExp, RegExp(DOTALL), RegExp(MULTILINE) only |

Regular expression options: `RegExp` has no options, `RegExp(DOTALL)` makes "." match all characters including newlines, `RegExp(MULTILINE)` makes "^" and "$" match the start/end of each line.

## Deduplication

When the event collection system or OASE agent is redundant, essentially identical events may be collected multiple times. This feature ingests only the first such event. Events whose values for the specified label key(s) (multiple allowed, AND condition) match are treated as duplicates, and deduplicated events are not passed into the evaluation flow.

Main input fields: deduplication setting name, priority (processed in ascending order, 1 to 2147483647), redundancy group (event collection target), and condition (label and expression: "ignore" = duplicate if all fields other than the specified ones match; "match" = duplicate if the specified fields match).

## Filter

A filter narrows down events based on label conditions. Events that satisfy all specified label conditions are extracted and become subject to rule evaluation. A single filter can be reused by multiple rules.

There are four search methods:

- **Unique**: Only a uniquely matching event is evaluated. If multiple events match, all are treated as undetected events.
- **Queuing**: Multiple matching events are evaluated in order from oldest to newest. Note that this may cause a rule to match multiple times.
- **Grouping (with/without period extension)**: Consecutive events sharing the same attributes (the same combination of label key and value) are treated as a single group, and only the first event is used (others are ignored). "With period extension" extends the TTL of the first event each time a new event occurs; "without period extension" groups events within the first event's TTL or a separately specified period.

Main input fields: Enabled (True/False), filter name, filter conditions (label key, condition ==/≠, condition value), search method, label and condition (for grouping targets), period (for grouping targets, 10 to 2147483647 seconds), and remarks. When grouping, a wildcard (`*`) can be used in the filter condition value to create a separate group for each label value.

## Action

An action is the concrete response processing executed when a rule matches. It defines the Conductor, operation, and target host to execute, and Ansible Playbooks are run through the Conductor. Since an action can reference the event's label values at execution time, the target and content can be dynamically changed per event. Configuring an action for a rule is optional (if not specified, only a conclusion event is generated). A single action can be reused by multiple rules.

Main input fields: action name, Conductor name, operation name, event linkage (host; whether to use the source event's `_exastro_host` label as the target host, default False), specified host, parameter sheet to use, and remarks. If no operation is specified, "host" and "parameter sheet to use" must be configured.

## Rule

A rule determines "which action to execute" and "what conclusion event to generate" based on filter results. It combines Filter A (required) and Filter B (optional) using a filter operator (AND / XOR / ->) to define the matching condition; when matched, it executes the action and generates a conclusion event based on the conclusion label settings. A priority can be set, and if multiple rules match, the one with the higher priority is applied.

Main input fields:

| Field | Description |
|---|---|
| Enabled | Select True/False to enable or disable the rule. |
| Rule Name | Arbitrary name (max 255 bytes). |
| Rule Label Name | The name set in the conclusion event's `_exastro_rule_name` label (max 255 bytes; cannot be changed later). |
| Priority | A positive integer; smaller values have higher priority. |
| Filter A / Filter Operator / Filter B | A and B (both must match), A xor B (either matches), A -> B (A occurs, then B occurs). |
| Pre-notification / Post-notification | Notification template file (max 2MB) and destination. |
| Action Name | The action to execute. |
| Action (inherit source event labels) | Whether to use the source event's labels as action parameters (default True). |
| Conclusion Event (inherit source event labels) | Whether the conclusion event inherits the source event's labels (default False). |
| Conclusion Label Settings | Set the label keys and values for the conclusion event. |
| TTL | The period (seconds) during which the event is treated as subject to rule evaluation. Minimum 10, maximum 2147483647, default 3600. |

Pre-work and post-work approval workflows are planned as future features.

## Evaluation Result

The Evaluation Result screen shows the action execution history (rule ID/name, status, action ID/name, Conductor instance ID/name, operation ID/name, specified host, parameter sheet used, event ID used, action parameters, conclusion event labels, registration date/time, remarks, etc.). Status values include: Evaluated, Executing, Awaiting Approval, Approved, Approval Rejected, Completed, Completed (Abnormal), Awaiting Completion Confirmation, Completion Confirmed, and Completion Confirmation Rejected. The "Details" button navigates to the Conductor work status check screen.

## Appendix: Notes on Infinite Loops

If a rule's conclusion event is configured so that it matches the same filter that leads back to that rule, an infinite loop occurs, continuously adding a large number of records to the event history and evaluation results. Disable the filter or rule as needed and review the configuration.

## Appendix: Searching Event History

- Object ID and Events Used: only exact-match searches are supported (partial match or no match is a validation error).
- Event Collection Setting ID, Event State, Event Type, Labels, Evaluation Rule Name: both exact-match and partial-match searches are supported.
- Event Collection Date/Time and Event Valid Date/Time: in addition to exact match, partial matches in the formats `YYYY/MM/DD`, `YYYY/MM/DD hh`, and `YYYY/MM/DD hh:mm` are supported (a truncated format or one ending in a colon results in an error).

## Appendix: Variables for Pre/Post-Notification Templates

Templates are written in Jinja2 format and can reference `rule.*` (rule ID, rule name, filter conditions, TTL, etc.), `action.*` (action ID, name, Conductor info, host, parameter sheet, etc.), `action_log.*` (status, registration date/time, conclusion event labels, etc.), `conductor.*` (execution status), and `event`/`events` (the event's labels and raw data). Key value mappings:

- `action_log.status`: Evaluated → Rule matched, Executing → Executing, Completed → Completed, Completed (Abnormal) → Completed (abnormal), etc.
- `rule.action_label_inheritance_flag` / `rule.event_label_inheritance_flag`: Use/Don't use, Inherit/Don't inherit
- `conductor.status`: Not executed, Executing, Paused, Completed normally, Completed abnormally, Completed with warning, Emergency stopped, Reservation cancelled, Unexpected error, etc.
- `conductor.note`: Notified / Not notified
