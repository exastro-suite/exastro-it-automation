# OASE機能の設定と利用方法

## OASEの利用手順

OASEの標準的な設定フローは以下の順に行います。

1. **ラベルの登録**: メニューグループ「ラベル」のラベル作成・ラベル付与で、イベントに使用するラベルを定義し、付与条件を設定する。冗長化構成の場合は重複排除も設定可能。
2. **フィルターの登録**: メニューグループ「ルール」のフィルターで、ルールに使用するラベル条件を設定する。
3. **アクションの登録**: メニューグループ「ルール」のアクションで、ルール判定にて条件を満たした際に実行する処理を登録する。
4. **ルールの登録**: メニューグループ「ルール」のルールで、判定条件と使用するアクションなどを設定する。

## イベントの基本概念

イベントは、監視システム（Zabbix、Prometheus、Datadogなど）が監視対象システムの状態変化（サービス停止、CPU高負荷など）を検知して作成するデータです。ExastroのOASEがこれを取得し、評価・自動対応を行います。

- OASEに取り込まれたイベントは、複数のラベル（キーと値のペア。例: `process: httpd`, `status: down`）形式で情報を保持します。ラベルは「ラベル付与」画面の設定に基づいて設定されます。
- イベントには「_exastro_」で始まるシステムラベルが自動付与されます（取得日時、TTLなど）。
- イベントには「通常イベント」と「結論イベント」の2種類があり、`_exastro_type` ラベルで区別されます。通常イベントは監視システムから収集したもの、結論イベントはルールマッチ後にOASEが生成するものです。結論イベントも評価フローの対象となるため、連鎖的な自動対応が可能です。
- 処理順序: ラベル付与 → フィルター → ルール評価 → （マッチ時）アクション実行。

### イベント履歴の項目

| 項目 | 説明 |
|---|---|
| オブジェクトID | 自動採番のため編集不可。 |
| イベント収集設定ID | OASE管理/イベント収集/イベント収集設定IDが元データ。 |
| イベント収集日時 | エージェントがイベントを取得した日時。 |
| イベント有効日時 | イベントの有効日時。 |
| イベント状態 | 検討中／未知／判定済み／時間切れ のいずれか。 |
| イベント種別 | イベント／結論イベント のいずれか。 |
| ラベル | 付与されたラベル情報。 |
| 評価ルール名 | OASE/ルール/ルールラベル名が元データ。 |
| 利用イベント | 評価に利用されたイベント。 |

正しく設定されていない場合、`_exastro_not_available` をキーとしたラベルが付与され未知イベントとして取り込まれます（レスポンスキー・イベントIDキーの設定誤りなど）。

## ラベル作成

ラベルはイベントに付与される属性情報で、キーと値のペアで構成されます。Exastroが自動付与する「システムラベル」（`_exastro_event_collection_settings_id`, `_exastro_fetched_time`, `_exastro_end_time`, `_exastro_agent_name`, `_exastro_agent_version`, `_exastro_type`, `_exastro_checked`, `_exastro_evaluated`, `_exastro_undetected`, `_exastro_timeout` など）と、ユーザーが設定する「ユーザーラベル」の2種類があります。

「ラベル作成」画面ではユーザーラベルのキー（半角英数字と `_-`、先頭に記号不可、最大255バイト）、カラーコード、備考を定義します。「ラベル付与」画面では受信イベントの特定フィールド値を条件に、固定値や特定フィールドの値をラベルへ設定します。付与されたラベルはフィルター条件やルール評価に使用されます。

## ラベル付与

「ラベル付与」画面の主な入力項目:

| 項目 | 説明 |
|---|---|
| ラベリング設定名 | 任意の設定名（最大255バイト）。 |
| イベント収集設定名 | イベント収集で登録した設定名を選択。 |
| 検索条件（キー/値のデータ型/比較方法/比較する値） | JMESPathでイベントのキーを指定し、データ型・比較方法（==, ≠, <, <=, >, >=, RegExp系）・比較値を設定。 |
| ラベル（キー/値） | 付与するラベルのキーとその値。正規表現使用時は空欄でマッチ結果をそのまま使う、または `\1` などキャプチャグループを参照できる。 |

値のデータ型ごとの比較方法制約:

| 値のデータ型 | 使用可能な比較方法 |
|---|---|
| 文字列・整数・小数 | RegExp系以外すべて |
| 真偽値・オブジェクト・配列・空判定 | ==（一致）、≠（不一致）のみ |
| その他 | RegExp, RegExp(DOTALL), RegExp(MULTILINE) のみ |

正規表現オプション: `RegExp`はオプションなし、`RegExp(DOTALL)`は「.」が改行を含む全文字にマッチ、`RegExp(MULTILINE)`は「^」「$」が各行の先頭・末尾にマッチ。

## 重複排除

イベント収集システムやOASEエージェントが冗長化されている場合、本質的に同一内容のイベントを複数取得しても先頭のイベントのみを取り込む機能です。指定したラベルキー（複数指定可、AND条件）の値が一致するイベントを重複と見なし、重複排除されたイベントは評価フローに投入されません。

主な入力項目: 重複排除設定名、優先順位（小さい順に処理、1〜2147483647）、冗長グループ（イベント収集先）、条件（ラベル・式：「を無視する」＝指定項目以外が一致で重複、「が一致する」＝指定項目が一致で重複）。

## フィルター

フィルターはラベル条件でイベントを絞り込む機能です。複数のラベル条件をすべて満たすイベントを抽出し、ルール評価の対象とします。1つのフィルターは複数ルールで再利用可能です。

検索方法は4種類:

- **ユニーク**: 条件に一致する一意のイベントのみ評価。複数一致した場合はすべて未知イベントとして処理。
- **キューイング**: 複数一致したイベントを古い順に評価。ルールに複数回マッチする可能性があるため注意。
- **グルーピング（期間延長あり／なし）**: 同一属性（ラベルのキー・値の組み合わせ）を持つ連続イベントを同一グループとみなし、先頭イベントのみ使用（他は無視）。「期間延長あり」はイベント発生毎に先頭イベントのTTLを延長、「期間延長なし」は先頭イベントのTTL内、または個別指定期間内でグルーピング。

主な入力項目: 有効(True/False)、フィルター名、フィルター条件（ラベルキー・条件==/≠・条件値）、検索方法、ラベル・条件（グルーピング対象）、期間（グルーピング対象、10〜2147483647秒）、備考。グルーピング時はフィルター条件値に `*`（ワイルドカード）を使用し、ラベル値ごとに個別グループを作成できる。

## アクション

アクションはルールマッチ時に実行される対応処理です。Conductor・オペレーション・対象ホストを指定して実行内容を定義し、Conductorを通じてAnsible Playbookが実行されます。アクション実行時はイベントのラベル値を参照できるため、イベントごとに動的に対象や内容を変更可能です。アクション設定はルールごとに任意（未指定時は結論イベント生成のみ）。1つのアクションは複数ルールで再利用可能。

主な入力項目: アクション名、Conductor名称、オペレーション名、イベント連携（ホスト、元イベントの`_exastro_host`ラベルを対象ホストにするか、デフォルトFalse）、指定（ホスト）、利用パラメータシート、備考。オペレーション未指定時は「ホスト」と「利用パラメータシート」を設定する。

## ルール

ルールはフィルター結果に基づき「どのアクションを実行するか」「どんな結論イベントを生成するか」を決定します。フィルターA（必須）とフィルターB（任意）をフィルター演算子（AND／XOR／->）で組み合わせて条件を定義し、マッチ時にアクションを実行、結論ラベル設定に基づき結論イベントを生成します。優先度を設定でき、複数ルールがマッチした場合は優先順位が高いものが適用されます。

主な入力項目:

| 項目 | 説明 |
|---|---|
| 有効 | True/Falseでルールの有効・無効を選択。 |
| ルール名 | 任意の名前（最大255バイト）。 |
| ルールラベル名 | 結論イベントの `_exastro_rule_name` ラベルに設定する名前（最大255バイト、後から変更不可）。 |
| 優先順位 | 正の整数、小さいほど優先。 |
| フィルターA / フィルター演算子 / フィルターB | A and B（両方マッチ）、A xor B（いずれかマッチ）、A -> B（Aの後にBが発生）。 |
| 事前通知／事後通知 | 通知テンプレートファイル（最大2MB）と通知先。 |
| アクション名 | 実行するアクション。 |
| アクション（元イベントのラベル継承） | アクションのパラメータとして元イベントラベルを使うか（デフォルトTrue）。 |
| 結論イベント（元イベントのラベル継承） | 結論イベントに元イベントラベルを継承するか（デフォルトFalse）。 |
| 結論ラベル設定 | 結論イベント用のラベルキー・値を設定。 |
| TTL | ルール評価対象として扱う期間（秒）。最小10、最大2147483647、デフォルト3600。 |

作業前・作業後承認待ちは今後の機能追加予定。

## 評価結果

評価結果画面ではアクション実行履歴（ルールID/名、ステータス、アクションID/名、ConductorインスタンスID/名称、オペレーションID/名、指定ホスト、利用パラメータシート、利用イベントID、アクションパラメータ、結論イベントラベル、登録日時、備考など）を閲覧できます。ステータスには判定済み・実行中・承認待ち・承認済み・承認却下済み・完了・完了（異常）・完了確認待ち・完了確認済み・完了確認却下済みがあります。「詳細」ボタンでConductorの作業状態確認に遷移できます。

## 付録: 無限ループの注意事項

あるルールの結論イベントが、そのルールに到達するフィルターにも再びマッチする設定の場合、無限ループとなりイベント履歴や評価結果に大量のレコードが登録され続けます。必要に応じてフィルターやルールを無効化し、設定を見直してください。

## 付録: イベント履歴の検索方法

- オブジェクトID・利用イベント: 完全一致のみ検索可能（部分一致・一致無しはバリデーションエラー）。
- イベント収集設定ID・イベント状態・イベント種別・ラベル・評価ルール名: 完全一致・部分一致とも検索可能。
- イベント収集日時・イベント有効日時: 完全一致に加え、`YYYY/MM/DD`, `YYYY/MM/DD hh`, `YYYY/MM/DD hh:mm` 形式の部分一致が可能（末尾が途切れた形式やコロン終わりはエラー）。

## 付録: 事前・事後通知テンプレートの変数

テンプレートはJinja2形式で、`rule.*`（ルールID、ルール名、フィルター条件、TTLなど）、`action.*`（アクションID、名称、Conductor情報、ホスト、パラメータシートなど）、`action_log.*`（ステータス、登録日時、結論イベントラベルなど）、`conductor.*`（実行状態）、`event`/`events`（イベントのラベルと元データ）が参照できます。主な値の対応:

- `action_log.status`: 判定済み→Rule matched、実行中→Executing、完了→Completed、完了（異常）→Completed (abnormal) など
- `rule.action_label_inheritance_flag` / `rule.event_label_inheritance_flag`: 利用する/しない、継承する/しない
- `conductor.status`: 未実行、実行中、一時停止、正常終了、異常終了、警告終了、緊急停止、予約取消、想定外エラー など
- `conductor.note`: 発令済み／未発令
